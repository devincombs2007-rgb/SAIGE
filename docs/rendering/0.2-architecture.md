# SAIGE 0.2 graphics architecture

**Status:** Proposal for agreement with Core. Nothing here changes a shared header until Core accepts the matching
contract in the RFC issue. Renderer-internal work (everything in §3) proceeds on feature branches meanwhile and does
not alter SAIGE 0.1 behavior.

0.1 draws one cube at one position with a fixed camera. 0.2 turns that into a renderer that can show a *scene*: a
camera you control, transformed instances of loaded meshes with materials and textures, correct occlusion, resource
lifetimes you can account for, measurements, and automated visual checks.

## 1. Scope (owner priorities, in dependency order)

| # | Capability | Where it lives | Needs a Core contract? |
|---|-----------|----------------|------------------------|
| 1 | Perspective camera, projection, frustum | `engine/render` | C-3 (camera state in `FrameView`) |
| 2 | Transform math (TRS, normals) and per-instance transforms | `engine/render` | C-1 (rotation/scale in `RenderInstance`) |
| 3 | Depth buffering and 3D occlusion tests | `engine/render` | no (already reverse-Z) |
| 4 | Visual regression harness | `engine/render/tests`, `tools/` | no |
| 5 | Diagnostics and performance instrumentation | `engine/render` | C-4 (optional, later) |
| 6 | glTF 2.0 loading to CPU mesh/material data | `engine/gfx_assets` | C-2 (asset identity) for runtime use |
| 7 | GPU mesh/texture resources, lifetimes | `engine/rhi*`, `engine/render` | no |
| 8 | Materials and textures (PBR metallic-roughness) | `engine/render`, `shaders/` | C-2 |
| 9 | Bindless descriptors (prerequisite for 7 and 8 at scale) | `engine/rhi*` | no |

## 2. Contracts to agree with Core

Every contract is **additive and source-compatible**: new fields get default member initializers, so Core's existing
aggregate initializations such as `instances.push_back({entity, position})` keep compiling and behaving the same.

### C-1 Transform
```cpp
struct Quat { float x{}, y{}, z{}, w{1.0F}; bool operator==(const Quat&) const = default; };  // unit quaternion
struct RenderInstance {
    Entity entity;
    Vec3 position;
    Quat rotation;         // NEW, identity by default
    Vec3 scale{1, 1, 1};   // NEW, positive components only in 0.2
    AssetId mesh;          // NEW (C-2), zero = built-in unit cube
    AssetId material;      // NEW (C-2), zero = built-in default material
};
```
- World transform is `T(position) * R(rotation) * S(scale)`, column vectors, in the engine standard: right-handed,
  Z-up, +X forward, +Y left, meters. A positive rotation about an axis is counter-clockwise looking from the positive end of
  that axis toward the origin ([coordinate standard](../standards/coordinate-system.md)).
- `rotation` is a unit quaternion stored `(x, y, z, w)`. The renderer normalizes defensively and treats zero or NaN
  as identity (logged once per entity, never a crash).
- Negative scale (mirroring, which flips triangle winding) is **undefined in 0.2**.
- `position` stays the instance origin. A mesh's own origin is its asset's concern: the 0.1 cube's origin is its base.
  glTF meshes keep their authored origin, converted to Z-up at import.

### C-2 Asset identity (Core owns it, per D-14)
- Core defines `struct AssetId { std::uint64_t value{}; }` (0 = invalid/none) in a new `include/saige/asset_id.hpp`.
  Proposal: a 64-bit value for 0.2 and a 128-bit GUID when the registry exists. The type is opaque to the renderer,
  which compares and hashes it only.
- **Resolution for 0.2 without a registry:** the application (Core) registers `AssetId -> file path` with the graphics
  asset cache at startup (`GraphicsAssets::register_mesh(AssetId, path)`), D-13's explicit paths. The renderer loads
  on first use, caches by id, and shows a fallback (a magenta cube) plus a one-time log line when a load fails.
- Streaming, async loads, hot reload and persistent GUIDs are out of scope for 0.2.

### C-3 Camera
```cpp
struct CameraView {              // NEW, in runtime.hpp
    Vec3 position;
    Quat rotation;               // camera looks along its local +X (the engine's forward axis), +Z up
    float fov_y_radians{1.0472F};
    float near_plane{0.1F};
};
struct FrameView { std::uint64_t tick; double alpha; std::span<const RenderInstance> instances;
                   const CameraView* camera{};  /* NEW: null = renderer default */ };
```
- Core owns camera entities and their behavior (follow, input, interpolation across `alpha`). The renderer owns the
  projection: **reverse-Z, infinite far plane**, aspect ratio taken from the surface. No far-plane field exists because
  infinity is the design; culling distance is a separate, later concern.
- `camera == nullptr` keeps the 0.1 follow camera, so 0.1 builds behave identically.

### C-4 Diagnostics (optional, later)
No shared-header change in 0.2. The sink already exposes `FrameSinkStats`; the renderer will add per-frame timing and
resource counters accessible from the application. A `"renderer"` block in the agent CLI JSON (schema v2) would be a
separate proposal once the field list settles.

### C-5 Determinism
Regression tests rely on the existing scripted-clock `saige::run` pattern and on the renderer deriving animation only
from `FrameView.tick` and `alpha`. No change needed. Keep that property: nothing in `RenderInstance` or `CameraView`
may be wall-clock driven.

## 3. Renderer-internal architecture

### 3.1 Camera and projection (`render/camera.hpp`)
`Camera` holds position, orientation, vertical FOV and near plane, and produces: view matrix, reverse-Z infinite
projection for an aspect ratio, combined view-projection, the six frustum planes (Gribb-Hartmann adapted to reverse-Z with
an infinite far plane, so five finite planes plus a degenerate far plane), world-space rays through a pixel, and a
screen-space projection helper used by tests. Orthographic projection is added when UI/shadow cascades need it.

### 3.2 Transforms (`render/transform.hpp`)
`Quat` (normalize, multiply, from axis-angle, to matrix), `Transform` (TRS), `Mat4` from TRS, and the normal matrix
(inverse transpose of the upper 3x3, needed for non-uniform scale). All column-major, column-vector, tested against
hand-computed values and the Z-up rotation rules.

### 3.3 Per-draw data: from push constants to a GPU scene
0.1 packs everything into one 128-byte push-constant block, which is full. 0.2 moves to:
- a **per-frame constants** uniform buffer (view-projection, camera, fog, sun),
- an **instance buffer** (storage buffer of model matrices, colors, material indices) written once per frame,
- a small push block carrying only the instance index.

That is the first step of the GPU-driven design in `render-architecture.md` and needs **bindless descriptors**
(descriptor-indexing features, one global descriptor set) in the RHI. Bindless lands before textures, so materials
never need per-draw descriptor sets.

### 3.4 Depth and occlusion
Already reverse-Z with `Greater` and a 32-bit float depth buffer. 0.2 adds tests that prove occlusion with pixels: a near
cube hides a far one regardless of draw order, intersecting cubes show the correct intersection, and the depth buffer
survives resize. No renderer change is expected; the tests are the deliverable.

### 3.5 Resource lifetime management
- Generational handles and the deferred-destruction queue already exist. 0.2 adds a **resource registry** per device
  that records creation (name, type, bytes, owning subsystem) and reports leaks at shutdown.
- `GpuMesh`/`GpuTexture` are reference-counted by the asset cache; the last release enqueues deferred destruction.
- Memory is tracked per category and compared with the device budget (`VK_EXT_memory_budget` when available).

### 3.6 Diagnostics and performance instrumentation
- CPU: scoped timers around extract, graph compile, record and submit, with min/avg/max over a rolling window.
- GPU: timestamp queries per pass (RHI `begin_timestamp`/`end_timestamp`, exposed through `Device`, no-op on devices
  without support), read back one frame late so the CPU never stalls.
- Counters: draw calls, triangles, barriers, descriptor writes, live resources and bytes by category.
- Output: a single `FrameDiagnostics` struct, printable and serializable to JSON for agents.
- Always compiled in, with near-zero cost when no consumer reads it.

### 3.7 Visual regression testing
- Deterministic scenes rendered offscreen on lavapipe (a CPU driver, so no GPU variance) with a fixed camera and the
  scripted clock.
- Golden images are checked in as binary PPM (no dependencies, byte-exact diffs in git), small (160x90).
- Comparison is tolerant: failure on RMSE above a threshold or too many pixels exceeding a per-channel delta, because lavapipe
  output can differ slightly across Mesa versions. On failure the test writes `actual`, `expected` and an amplified `diff`
  image, which CI uploads as an artifact.
- `SAIGE_UPDATE_GOLDENS=1` regenerates goldens locally. Updating a golden is always a reviewed, visible diff.
- Goldens record the Mesa and driver versions in a sidecar text file so a legitimate driver change is diagnosable.

### 3.8 glTF 2.0 (`engine/gfx_assets`)
Phase 1 (CPU data, no dependencies): a small JSON parser, then `.gltf` + external `.bin`, `.glb`, and base64 data URIs;
accessors with all component types and normalization, strided bufferViews, sparse accessors (rejected with a clear error
in v1), meshes and triangle primitives (`POSITION`, `NORMAL`, `TANGENT`, `TEXCOORD_0`, `COLOR_0`, indices; missing
normals are generated), nodes with TRS or matrix transforms, and metallic-roughness materials with texture references.
Import converts from glTF's Y-up to the engine's Z-up as a proper rotation (winding preserved) and applies the yaw that maps
glTF's +Z front to +X. Malformed input yields a descriptive error, never a crash, and fuzz-style tests cover truncation.

Phase 2: images (PNG/JPEG decode needs a library decision: stb_image, a single public-domain header, proposed in D-03
terms with a pinned version) and GPU upload. Skins, animation and morph targets stay with the animation contract (#7).

## 4. Order of work and verification

1. Camera, transforms, occlusion tests (no Core dependency).
2. Visual regression harness and the first goldens.
3. Diagnostics and CPU timing; GPU timestamp support in the RHI.
4. glTF CPU loader with an original fixture mesh.
5. Bindless descriptors, then GPU meshes and the instance buffer.
6. Textures and materials.

Each step lands as its own PR with tests that run on the null backend and, where pixels matter, on lavapipe.
SAIGE 0.1 behavior and its acceptance test stay unchanged throughout.
